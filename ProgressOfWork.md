**ЭТАП 2 ЗАВЕРШЁН И ПОДТВЕРЖДЁН РУЧНЫМ ТЕСТИРОВАНИЕМ.**

Заглушки (реализуются на следующих этапах):

- `app/llm_service.py` — возвращает фиксированный ответ вместо обращения к LLM.
- `app/database.py` — SQLite не подключён, «сохранение» только в лог.
- `app/rate_limiter.py` — лимиты не применяются, запрос разрешается всегда.

Примечание об ограничении LLM:

Модель `openai/gpt-5.6-luna` через ProxyAPI **не поддерживает настройку
`temperature`** — провайдер использует дефолтное значение (1).

Принятое архитектурное решение:

- Параметр `temperature` ПЕРЕДАЁТСЯ в запросы к LLM
  (`client.chat.completions.create(..., temperature=config.TEMPERATURE)`) —
  для гибкости при смене модели или провайдера, где `temperature`
  поддерживается.
- Если провайдер вернёт ошибку 400, связанную с `temperature`, — повторить
  запрос БЕЗ `temperature`, залогировать факт и продолжить работу.
- На этапе 2 LLM — заглушка, запросов к провайдеру нет; решение зафиксировано
  в docstring `app/llm_service.py` и будет реализовано на этапе 3.

Подробнее — `README.md`, раздел «Ограничения провайдера».

## Этап 3. ПОДКЛЮЧЕНИЕ LLM — инструкция для следующего агента

  это этапы 4 и 5, их НЕ трогаем.

### Задача этапа 3

Заменить заглушку в `app/llm_service.py` на реальный вызов LLM через
ProxyAPI (OpenAI-совместимый клиент), с обработкой ошибок и fallback.

### Как делать (рекомендации, сверяться с ТЗ `prompts/`)

1. **Клиент**: `from openai import OpenAI`;
   `OpenAI(api_key=config.PROXY_API_KEY, base_url=config.OPENAI_BASE_URL)`
   (значения уже в `.env`, ключ реальный — проверять не нужно).
2. **Вызов**: `client.chat.completions.create(model=config.OPENAI_MODEL,
   messages=[...], temperature=config.TEMPERATURE)`.
3. **Ключевое архитектурное решение по `temperature`** (согласовано с
   пользователем, зафиксировано в docstring `llm_service.py` и README):
   модель `openai/gpt-5.6-luna` через ProxyAPI может не поддерживать
   `temperature`. Поэтому: передаём `temperature` ВСЕГДА; при
   `openai.BadRequestError`, связанной с `temperature`, — повторяем запрос
   БЕЗ него и логируем это. Остальные ошибки — не ретраить вслепую.
4. **Системный промпт**: в `prompts/` лежит только текст ТЗ, промпта для
   модели там НЕТ — составить и положить в код (или отдельный модуль).
   Требования из ТЗ: категория из `billing|network|service|other`; черновик
   ответа 1–6 предложений; уверенность `low|medium|high`; флаг эскалации.
   Просить модель отвечать СТРОГО JSON без markdown-обёртки.
5. **Парсинг**: снять `response.choices[0].message.content`, при наличии
   обёрнуть/очистить ```` ```json ````-фенсы, `json.loads`, прогнать через
   `TriageResponse` (валидность контракта гарантировать).
6. **Fallback при ошибке LLM/парсинга**: не ронять эндпоинт — вернуть
   безопасный ответ (`category="other"`, `draft_reply` о невозможности
   автоматической обработки, `confidence="low"`, `escalate=true`) и
   залогировать ошибку через `app.logger`.
7. **Сигнатуру `triage_request(request)` и `app/api.py` не менять** —
   интеграция уже готова, достаточно новой реализации внутри llm_service.

### Как проверять

- Запуск: `venv\Scripts\activate` → `uvicorn main:app --reload`
  (из корня проекта; Swagger: http://localhost:8000/docs).
- Запросы из `tests/test_requests.http` (валидные → 200 с реальными
