Примечание об ограничении LLM:

Модель `openai/gpt-5.6-luna` через ProxyAPI **не поддерживает настройку
`temperature`** — провайдер использует дефолтное значение (1).

Уточнение 2026-10-04 (этап 3): в живом запросе провайдер принял
`temperature=1.0` без ошибки, поэтому ограничение стоит считать
потенциальным, а не подтверждённым; реализованный повтор при `400` —
страховка.

Принятое архитектурное решение:

- Параметр `temperature` ПЕРЕДАЁТСЯ в запросы к LLM
  (`client.chat.completions.create(..., temperature=config.TEMPERATURE)`) —
  для гибкости при смене модели или провайдера, где `temperature`
  поддерживается.
- Если провайдер вернёт ошибку 400, связанную с `temperature`, — повторить
  запрос БЕЗ `temperature`, залогировать факт и продолжить работу.
- На этапе 2 LLM — заглушка, запросов к провайдеру нет; решение зафиксировано
  в docstring `app/llm_service.py` и будет реализовано на этапе 3.

### Отличия от инструкции передачи (важно для следующих этапов)

Инструкция этапа 3 была написана до реализации и местами расходилась с
кодом. Что сделано иначе и почему:

1. **Категории.** Инструкция п. 4 требовала `billing|network|service|other`,
   но контракт `app/models.py` (его менять нельзя) определяет
   `billing|support|complaint|other`. Взято значение из контракта — иначе
   ответы модели не проходили бы валидацию `TriageResponse`.
2. **Сигнатура и `app/api.py`.** Инструкция п. 7 просила не менять
   `triage_request(request)` и `app/api.py`. В коде этапа 2 функцией
   заглушки была `classify_request(text, channel, client_id)`, а не
   `triage_request(request)`, поэтому импорт в `app/api.py` обновлён в
   любом случае. Итоговая сигнатура — `triage_text(text, channel)`;
   `client_id` в LLM не передаётся (модель его не использует, а в лог он
   попадает на уровне эндпоинта).
3. **Повтор при `temperature`.** Инструкция п. 3 («остальные ошибки не
   ретраить») оставлена в силе; реализован ровно один повтор — при `400`
   с упоминанием `temperature` снимается неподдерживаемый параметр, а не
   выполняется ретрай по сети или по битому JSON. Это страховка на случай
   отказа провайдера: в живом запросе 2026-10-04 (`TEMPERATURE=1.0`)
   провайдер параметр принял, повтор не сработал ни разу.
4. **Статус репозитория.** В инструкции сказано «рабочая папка не под git» —
   на 2026-10-04 проект под git, есть `origin`
   (`https://github.com/ElenaBelyasnik/vpk04-1-triage-ai-service`),
   `main` синхронизирован с `origin/main`.

## Этап 4. Сохранение обращений в SQLite

Дата: 2026-10-09.

### Выполнено

`app/database.py` — заглушка («сохранение только в лог») заменена реальной
записью на стандартном `sqlite3` (без новых пакетов в `requirements.txt`):

- `init_db()` — создаёт файл БД и таблицу `tickets`
  (`CREATE TABLE IF NOT EXISTS`, идемпотентно); вызывается один раз при
  старте сервиса.
- `save_ticket(*, client_id, channel, text, category, confidence, escalate,
  draft_reply, error) -> int | None` — аргументы только по имени;
  параметризованный `INSERT` (`?`) — текст обращения не может стать
  SQL-командой; `escalate` хранится как `0`/`1` (`None` остаётся `NULL`);
  возвращает `id` вставленной строки.
- `get_ticket(ticket_id) -> dict | None` — чтение одной записи по id
  (для ручной проверки).
- Путь к файлу: относительный `DB_PATH` разрешается от корня проекта
  (`PROJECT_ROOT`), а не от текущей директории запуска; `_connect()`
  создаёт родительскую папку файла БД.
- Ошибки БД наружу НЕ выпускаются: `init_db`/`save_ticket`/`get_ticket`
  логируют их уровнем `ERROR` и возвращают — обращение уже обработано,
  падать с 500 из-за хранилища значит ломать то, что важнее.
- Соединение открывается на каждую операцию и закрывается в `finally`
  (съёмка вопросов о потоках uvicorn и `--reload`; файл SQLite открывается
  за доли миллисекунды).
- `created_at` подставляет сам SQLite (`CURRENT_TIMESTAMP`).

`app/llm_service.py`:

- добавлена `triage_text_with_error(text, channel) -> tuple[dict, str | None]`
  — вместе с результатом отдаёт причину сбоя (раньше она жила только в
  логе); прежняя `triage_text(text, channel)` делегирует ей, поведение
  этапа 3 не изменилось.

`app/api.py`:

- после получения ответа (успех или fallback) — `save_ticket(...)`: поля
  берутся из `response`, в БД попадает ровно то, что увидел клиент;
- причина сбоя LLM кладётся в колонку `error` (обрезка `MAX_ERROR_LENGTH=500`
  для читаемости), у успешных ответов — `NULL`;
- `ticket_id` добавлен в итоговую строку лога — связывает лог со строкой БД.

`app/config.py`:

- `DB_PATH` — путь к файлу БД из `.env` (дефолт `tickets.db`);
- `LOG_MODE` — режим файла логов (дефолт `write`).

`app/logger.py`:

- `LOG_MODE=write` — `logs/app.log` пересоздаётся при каждом запуске
  (файл создаёт только первый FileHandler, остальные дописываются в него);
  `LOG_MODE=append` — файл накапливается между запусками.

`main.py`:

- `lifespan`: до приёма первых запросов вызывается `init_db()`; ошибка
  инициализации не роняет сервис (лог `WARNING`, аудит может не писаться).

`.env` / `.env.example` — добавлены `DB_PATH=tickets.db` и `LOG_MODE=write`
с комментариями.

`tests/test_requests.http` — сценарии этапа 4: № 13-14 (обычные запросы →
строка в `tickets`, `error = NULL`), № 15 (неразборчивый текст →
`escalate = 1`), № 16 (испорченный ключ → причина в `error`), № 17
(чтение `get_ticket(id)`).

`README.md` — раздел «База данных (SQLite)» (схема, команды просмотра),
обновлены «Как это работает», «Fallback» (колонка `error`), «Структура
проекта», «Проверка» (№ 13-17, `LOG_MODE`).

### Решения, отличные от буквального текста промпта (согласованы с пользователем)

1. **`LOG_MODE` вместо жёсткой замены `a`→`w`** (п. 11 промпта требовал
   пересоздавать файл логов всегда). Сделано настраиваемым: по умолчанию
   `write` (промпт соблюдён), при `append` — накопление истории. Причина:
   потеря логов между запусками неудобна при отладке, а обратно переключать
   код каждый раз — хуже.
2. **Имя файла БД — `tickets.db`** (зафиксировано пользователем; `DB_PATH`
   позволяет переопределить в `.env`).
3. **Причина ошибки LLM сохраняется в колонку `error`** — промпт требовал
   хранить ошибки; реализовано через `triage_text_with_error`, чтобы текст
   причины не терялся между слоем LLM и записью.

### Проверка этапа 4

- Старт сервиса: `init_db()` создал файл `tickets.db` и таблицу — в логе
  «БД готова: файл=..., таблица=tickets».
- Живые запросы через `POST /triage` (ProxyAPI): ответ 200, в логе
  «Обращение сохранено в БД: id=N, ...»; строки прочитаны из `tickets.db` —
  все поля заполнены ответом модели, `escalate` 0/1, `error = NULL` на
  успехе.
- Чтение `get_ticket(id)` — возвращает dict строки, `None` для
  несуществующего id.
- UTF-8: текст обращения сохраняется в БД без искажений (проверено
  запросом из Python через `requests`; **важно**: тело запроса, набранное
  напрямую в консоли PowerShell, искажается самой консолью — не трогать
  это как баг сервиса).
- `tickets.db` не попадает в git (`git check-ignore` подтвердил правило
  `*.db` из `.gitignore`).

### Известные особенности

- При `LOG_MODE=write` (дефолт) логи предыдущих запусков теряются — это
  осознанный дефолт для отладки; история нужна → `LOG_MODE=append`.
- `save_ticket` пишет каждое обработанное обращение, включая fallback —
  БД растёт на каждый запрос; ротация/очистка не предусмотрены (вне рамок
  промпта).
