# Triage AI Service

MVP-сервис на FastAPI для предварительной обработки (триажа) клиентских
обращений: приём обращения по API, определение категории и подготовка
черновика ответа.

## Текущее состояние

- **Этап 5 завершён**: лимитирование запросов по `client_id`
  (`RATE_LIMIT_PER_MINUTE` из `.env`, по умолчанию 5 запросов в минуту;
  размер окна настраивается `RATE_WINDOW_SECONDS`, по умолчанию 60 секунд) —
  при превышении клиент получает `429` и запись в лог (см. раздел
  «Лимитирование запросов»).
- **Этап 4 завершён**: SQLite — обращение и результат его обработки
  записываются в таблицу `tickets` файла `tickets.db` (см. раздел
  «База данных»).
- **Этап 3 завершён** (подтверждён ручным тестированием пользователем):
  `POST /triage` обращается к LLM через ProxyAPI — категорию и черновик
  ответа формирует модель, а не заглушка.
- **Этап 2 завершён** (подтверждён ручным тестированием через Swagger UI):
  эндпоинт `POST /triage` с полной валидацией входных данных (Pydantic)
  и логированием в консоль и `logs/app.log`.

## Как это работает

1. FastAPI валидирует вход моделью `TriageRequest` (несоответствие → 422,
   до обращения к LLM).
2. `app/api.py` вызывает `triage_text(text, channel)` из `app/llm_service.py`.
3. `triage_text` отправляет запрос в ProxyAPI (`PROXY_API_KEY`,
   `OPENAI_BASE_URL`, `OPENAI_MODEL`) с системным промптом, который требует
   ответ **строго JSON**.
4. Ответ разбирается (`_extract_json`), проходит валидацию (`_validate`) и
   возвращается как `TriageResponse`.
5. Обращение и ответ на него записываются в SQLite — таблицу `tickets`
   (`save_ticket`): на успехе и на фолбэке. Ошибка записи в БД логируется
   уровнем `ERROR` и не меняет ответ клиенту.

Контракт API (`app/models.py`) на этапе 3 **не менялся**.

## Fallback

Если LLM недоступна или ответ некорректен, эндпоинт не падает, а отдаёт
безопасный ответ и пишет причину в лог:

```json
{
  "category": "other",
  "draft_reply": "Обращение передано оператору.",
  "confidence": "low",
  "escalate": true
}
```

Fallback срабатывает при: сетевой ошибке и таймауте; ошибочном статусе
провайдера (401 ключ, 429 лимит, 5xx); ответе, из которого не удалось
извлечь JSON; недопустимых значениях полей (`category` вне
`billing|support|complaint|other`, `confidence` вне `high|medium|low`,
`escalate` не `bool`, пустой `draft_reply`).

Причина сбоя пишется в лог уровнем `WARNING`/`ERROR` и сохраняется в БД —
в колонку `error` таблицы `tickets` (у успешных ответов эта колонка `NULL`).

## База данных (SQLite)

- Файл — `tickets.db` в корне проекта (путь берётся из `DB_PATH` в `.env`;
  относительный путь разрешается от корня проекта, не от текущей директории).
- Файл и таблицу создаёт `init_db()` при старте сервиса (в `main.py`,
  до приёма первых запросов). Файл БД в git не попадает (`*.db` в `.gitignore`).
- Таблица `tickets`: `id` (PK AUTOINCREMENT), `created_at` (подставляет
  SQLite), `client_id`, `channel`, `text`, `category`, `confidence`,
  `escalate` (`0`/`1`), `draft_reply`, `error` (причина сбоя LLM, у успешных
  — `NULL`).
- Записывается **каждое обработанное обращение**: и успешное, и fallback.
- Все SQL-запросы параметризованы (`?`) — текст обращения не может стать
  SQL-командой.
- Ошибка записи в БД **не меняет ответ клиенту**: запрос остаётся `200`,
  в лог уходит `ERROR` («Не удалось сохранить обращение в БД ...»).

Как посмотреть записи — утилитой `sqlite3` (если установлена):

```bash
sqlite3 tickets.db "SELECT id, client_id, category, escalate, error FROM tickets ORDER BY id DESC LIMIT 5;"
```

или стандартным модулем Python (работает без установки `sqlite3`):

```bash
python -c "import sqlite3; c = sqlite3.connect('tickets.db'); c.row_factory = sqlite3.Row; [print(dict(r)) for r in c.execute('SELECT * FROM tickets ORDER BY id DESC LIMIT 5')]"
```

Прочитать одну запись по id можно функцией `get_ticket` (из `app/database.py`):

```bash
python -c "from app.database import get_ticket; print(get_ticket(1))"
```

## Лимитирование запросов (этап 5)

`app/rate_limiter.py` подключён к эндпоинту `POST /triage` и ограничивает
частоту обращений по `client_id` (поле `client_id` в запросе):

- **`RATE_LIMIT_PER_MINUTE`** из `.env` — максимальное число запросов
  в минуту на одного клиента (по умолчанию 5).
- **`RATE_WINDOW_SECONDS`** из `.env` — размер скользящего окна в секундах
  (по умолчанию 60 — «в минуту»; окно можно настроить, например, на 120
  секунд — тогда лимит считается «N запросов за 2 минуты»).
- **Скользящее окно**: учитываются запросы за последние
  `RATE_WINDOW_SECONDS` секунд (не «с начала минуты»).
- При превышении лимита клиент получает `429` с JSON:

  ```json
  {
    "error": "rate_limit_exceeded",
    "detail": "Слишком много запросов. Попробуйте через минуту."
  }
  ```

  а в лог (консоль и `logs/app.log`) пишутся `WARNING` модуля
  `triage.rate_limiter` («RateLimiter: превышен лимит для client_id=...
  — запросов в окне (N секунд): K, лимит: M/мин», где N —
  `RATE_WINDOW_SECONDS`) и `WARNING` модуля `triage.api` («RateLimiter:
  отказано в запросе для client_id=...»).
- Для разных `client_id` счётчики независимы.
- Хранилище лимитов — память процесса (словарь под `threading.Lock`):
  при перезапуске сервиса история обнуляется; БД/Redis/файлы не
  используются (простая реализация по заданию).

### Как проверить

1. Убедиться, что в `.env` стоит `RATE_LIMIT_PER_MINUTE=5` (или меньше
   для быстрой проверки).
2. Отправить **6+ запросов с одним `client_id`** (например, через
   `curl`/Postman/Swagger UI):

   ```bash
   curl -X POST http://localhost:8000/triage -H 'Content-Type: application/json' -d '{"client_id":"test","text":"Пропал заказ","channel":"email"}'
   ```

3. Убедиться, что с 6-го запроса приходит `429`.
4. Проверить лог (`logs/app.log`) — в нём `WARNING` о превышении лимита.
5. Отправить запрос с **другим `client_id`** — он не должен получить `429`.
6. Подождать ~`RATE_WINDOW_SECONDS` секунд (по умолчанию 60) и повторить
   запрос с тем же `client_id` — лимит сбрасывается (скользящее окно).

    одного клиента за минуту → 200 (каждый засчитывается в скользящее
    окно 60 секунд); № 23 — шестой запрос того же клиента в том же окне →
    429; № 24 — запрос другого клиента сразу после № 23 → 200 (счётчики по
    `client_id` независимы).
- Проверка записи в БД: после любого запроса в логе строка
  «Обращение сохранено в БД: id=N, ...»; ту же строку можно прочитать
  из `tickets.db` (команды — в разделе «База данных»).
- Проверка fallback: временно испортить ключ или имя модели в `.env`
  (**не коммитить**) → ожидается 200 + `escalate=true`, причина в логе
  и в колонке `error` таблицы `tickets`.
- Логи: `logs/app.log`. Пишутся канал, длина текста, сырой ответ модели
  (не длиннее 300 символов), ошибки, срабатывания fallback и факт записи
  в БД. **Текст обращения в лог не попадает** — он сохраняется только
  в БД.
- Режим файла логов настраивается переменной `LOG_MODE` в `.env`:
  `write` (по умолчанию) — `logs/app.log` пересоздаётся при каждом
  запуске; `append` — файл накапливается между запусками.

## Ограничения провайдера

На этапе 2 зафиксировано, что модель `openai/gpt-5.6-luna` через ProxyAPI
может не поддерживать настройку параметра `temperature` (провайдер использует
дефолтное значение).

Принятое архитектурное решение: параметр `TEMPERATURE` **передаётся
всегда** — если модель или провайдер поменяются на поддерживающие
`temperature`, настройка заработает без правок в коде. Если провайдер ответит
`400` с упоминанием `temperature`, запрос **повторяется без этого параметра**,
а сам факт фиксируется в логе уровнем `WARNING`. Повтор — единственный, и
срабатывает он только на эту конкретную ошибку; сетевые сбои и битый ответ не
ретраятся, а сразу уходят в fallback.

Статус на 2026-10-04: в живом запросе к ProxyAPI провайдер параметр
`temperature=1.0` **принял**, повтор не понадобился. Поведение повтора
проверено на подменённом ответе провайдера (искусственная ошибка `400`).
Повтор срабатывает **только** при ошибке `400` от провайдера с упоминанием
`temperature`. В штатной работе (модель `openai/gpt-5.6-luna`) повтор
**не** срабатывает — провайдер принимает `temperature`. Логика повтора
оставлена как защита на случай смены модели или провайдера.

```json
POST /triage
{
```

## Пример ответа

```json
{
  "category": "billing",
  "draft_reply": "Здравствуйте! Проверьте, пожалуйста, корректность адреса доставки счетов в личном кабинете. Мы сверим начисления за текущий период и свяжемся с вами в течение рабочего дня.",
  "confidence": "high",
  "escalate": false
}
```

Поля `category`, `draft_reply` и `confidence` формирует модель, поэтому
`draft_reply` между запросами различается. При этом значения всегда остаются
в пределах, гарантированных `TriageResponse`: `category` — одна из
`billing|support|complaint|other`, `confidence` — одна из `high|medium|low`,
`escalate` — строго `bool`.
